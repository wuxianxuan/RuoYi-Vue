# 尾盘推荐实验说明（v2：不追高口径 + 次日表现回填）

> **2026-10 重构说明**：117 现在只读 119 生成的 `stock_recommend_pool`，按 `TREND` / `LIMIT_UP`
> 两个来源分别过滤，固定名额为趋势 5 + 涨停 5；`stock_tail_recommend_record` 已增加 `source`，
> 118 按来源分别统计。本文档保留原实验口径与 SQL 参考。

> 目的：把「凭感觉觉得推得太多、涨得太高」变成可量化的问题。每天推荐时记录指标快照，次日收盘后自动回填表现，
> 跑一段时间后用数据判断这套口径是否真的降低了次日回调，以及阈值该往哪个方向调。

## 一、这次实验要回答的三个问题

1. **挡没挡住**：涨幅上限、近5日涨幅、MA5乖离、换手/量比区间、成交额这几道闸门，实际淘汰了多少票？
2. **挡对没有**：被挡掉之后，推荐票的次日回调（最大浮亏）是不是真的变小了？
3. **还有没有票**：口径收紧后每天还能推出 5~10 只，还是经常 0 只？

## 二、每天的运行链路

```
交易日 14:45  stockTailRecommendTask
              ├─ 生成「尾盘推荐_日期」分组
              ├─ 邮件推送到手机
              ├─ 写 stock_tail_recommend_record（推荐 + 被挡候选的指标快照，含淘汰原因）
              └─ 写 stock_tail_recommend_run（本次筛选漏斗）

下一交易日 16:10  stockTailRecommendEvalTask
              ├─ 用次日日K回填：次日开/高/低/收、相对推荐价的收益、最大浮盈、最大浮亏
              └─ 日志分别打印"推荐组 / 被挡组"最近 300 条的滚动统计
```

**为什么被挡掉的票也要记录**：只看推荐组的表现，永远无法判断闸门是不是挡错了方向。
如果「被挡组」的次日表现和「推荐组」一样甚至更好，说明那条闸门没有区分度，应该放开；
反之如果被挡组明显更差，闸门就有效。这是唯一能证明"收紧有用"的数据。

**候选池新鲜度校验**：尾盘推荐启动时会先查 `stock_rising_state` 的最后更新时间，如果早于基准日（上一交易日），
直接报错并让任务失败，不会拿旧池子静默推荐。所以 `stockRisingTrendTask` 漏跑或失败时，你看到的是一份失败记录，
而不是一份"看起来正常"的推荐。

RuoYi 定时任务管理页面配置：

| 任务 | 调用目标字符串 | 建议 cron |
|---|---|---|
| 尾盘推荐 | `stockTailRecommendTask.execute()` | `0 45 14 ? * MON-FRI` |
| 次日表现回填 | `stockTailRecommendEvalTask.execute()` | `0 10 16 ? * MON-FRI` |

回填任务依赖当天的日K已同步，所以必须排在 `stockKlineSyncTask` 之后；没同步也不丢数据，下次运行会自动补上。

## 三、建表

执行 [`sql/stock_tail_recommend.sql`](../sql/stock_tail_recommend.sql)，创建两张表：

- `stock_tail_recommend_record`：每个候选股票一行（含被挡的），含推荐时指标 + 淘汰原因 + 次日表现
  （唯一键 `trade_date + stock_code`，删除分组后重算会覆盖）。
- `stock_tail_recommend_run`：每次运行的候选数/命中数/推荐数 + 各过滤条件淘汰数量（唯一键 `trade_date + rule_version`）。

数据量：候选约 300~400 只/日，一年约 10 万行，对 MySQL 没有压力。

## 四、关键字段

| 字段 | 含义 | 为什么关心 |
|---|---|---|
| `picked` / `reject_reason` | 是否被推荐 / 淘汰原因 | 支撑"推荐组 vs 被挡组"对比 |
| `rec_price` | 推荐时价格（14:45） | 次日表现的计算基准 |
| `close_pct` / `gain_5d` | 当日涨幅 / 截至昨日的近5日涨幅 | 判断是不是"已经涨透" |
| `bias_ma5` | 相对 MA5 乖离 | 均值回归风险 |
| `close_pos` / `tail_change` | 收盘位 / 尾盘30分钟涨跌 | 当日强度 |
| `next_change_pct` | 次日收盘相对推荐价 | 持有到次日收盘的收益 |
| `next_max_gain_pct` / `next_max_drawdown_pct` | 次日最大浮盈 / 最大浮亏 | 回调风险的直接度量 |
| `rank_no` | 推荐排名（评分降序） | 验证"前几名是不是更好" |
| `rule_version` | 规则版本 | 不同参数组合之间对比 |

## 五、怎么看结果（直接复制执行）

**1）推荐组的总体表现（先看这个）**

```sql
select count(*)                                                              as 样本数,
       round(avg(next_change_pct), 2)                                        as 次日平均涨幅,
       round(sum(next_change_pct > 0) / count(*) * 100, 1)                   as 上涨占比,
       round(avg(next_max_gain_pct), 2)                                      as 平均最大浮盈,
       round(avg(next_max_drawdown_pct), 2)                                  as 平均最大浮亏
from stock_tail_recommend_record
where eval_status = 'DONE'
  and picked = 1;
```

判断标准很朴素：**平均最大浮亏明显收窄、上涨占比不低于 50%**，就说明收紧有效；如果浮亏没变小、数量还少了一半，说明闸门开错了地方。

**2）按规则版本对比（做过 A/B 之后）**

```sql
select rule_version,
       count(*)                                                    as 样本数,
       round(avg(next_change_pct), 2)                              as 次日平均涨幅,
       round(sum(next_change_pct > 0) / count(*) * 100, 1)         as 上涨占比,
       round(avg(next_max_drawdown_pct), 2)                        as 平均最大浮亏
from stock_tail_recommend_record
where eval_status = 'DONE'
  and picked = 1
group by rule_version;
```

**3）排名是不是越靠前越好**

```sql
select rank_no,
       count(*)                                as 样本数,
       round(avg(next_change_pct), 2)          as 次日平均涨幅,
       round(avg(next_max_drawdown_pct), 2)    as 平均最大浮亏
from stock_tail_recommend_record
where eval_status = 'DONE'
  and picked = 1
group by rank_no
order by rank_no;
```

如果前 3 名和 8~10 名没差别，说明评分公式没起作用，可以直接砍到 5 只。

**4）验证"涨得多的是不是次日更差"（这是本次实验的核心假设）**

```sql
select case when close_pct < 3 then 'a. 0~3%'
            when close_pct < 5 then 'b. 3~5%'
            else 'c. 5~7%' end          as 当日涨幅分档,
       count(*)                          as 样本数,
       round(avg(next_change_pct), 2)    as 次日平均涨幅,
       round(avg(next_max_drawdown_pct), 2) as 平均最大浮亏
from stock_tail_recommend_record
where eval_status = 'DONE'
  and picked = 1
group by 当日涨幅分档
order by 当日涨幅分档;
```

**5）看漏斗：哪条闸门卡得最狠**

```sql
select trade_date, candidate_count, hit_count, picked_count, reject_summary
from stock_tail_recommend_run
order by trade_date desc
limit 10;
```

**6）推荐组 vs 被挡组：闸门到底有没有区分度（最重要）**

```sql
select case when picked = 1 then '推荐组' else '被挡组' end as 组别,
       count(*)                                             as 样本数,
       round(avg(next_change_pct), 2)                       as 次日平均涨幅,
       round(sum(next_change_pct > 0) / count(*) * 100, 1)  as 上涨占比,
       round(avg(next_max_drawdown_pct), 2)                 as 平均最大浮亏
from stock_tail_recommend_record
where eval_status = 'DONE'
group by picked;
```

**7）按淘汰原因拆开：哪条闸门挡错了（挡掉了反而涨得更好的票）**

```sql
select ifnull(reject_reason, '通过(推荐)')  as 原因,
       count(*)                             as 样本数,
       round(avg(next_change_pct), 2)       as 次日平均涨幅,
       round(avg(next_max_drawdown_pct), 2) as 平均最大浮亏
from stock_tail_recommend_record
where eval_status = 'DONE'
group by ifnull(reject_reason, '通过(推荐)')
order by 平均最大浮亏;
```

如果某条原因（比如「近5日已涨透」）挡掉的票平均涨幅比推荐组还高、浮亏却更小，说明这条阈值定错了，应当放宽或去掉。

## 六、调参顺序

先按默认跑 5~10 个交易日，看漏斗和分档结果再动，不要一次改多个参数。

| 现象 | 先动这个 | 再动 | 最后才动 |
|---|---|---|---|
| 命中太少（经常 0~3 只） | `max-gain-5d`：15 → 20 | `min-turnover-amount`：1.0 → 0.5 | `max-close-gain`：7 → 8 |
| 命中太多（>10，top-n 一直截断） | `max-close-gain`：7 → 6 | `max-bias-ma5`：5 → 3 | `min-close-pos`：0.7 → 0.8 |
| 次日浮亏仍然大 | 看第 4 条 SQL，若 5~7% 档最差 → `max-close-gain` 降到 5 | 若乖离大的最差 → `max-bias-ma5` 降到 3 | 关掉 `include-limit-up`（首二板不放进来） |
| 上涨占比低（<45%），但浮亏不大 | 说明是选股方向问题，不是追高问题 | 考虑换 `min-tail-change`（-0.5 → 0）要求尾盘更稳 | — |
| **某条闸门挡掉的票反而更好**（第 7 条 SQL） | 直接放宽或去掉这条阈值（通常是 `max-gain-5d` / `max-bias-ma5`） | 先确认样本数 ≥ 50 再下结论 | 观察一个版本周期后再回滚 |

每改一次参数，**同步改 `rule-version`**（`application.yml` 的 `stock.tail-recommend.rule-version`），否则新旧口径的样本会混在一起，对比失真。

## 七、A/B 的做法

1. 参数 A（当前默认）：`rule-version: v2`，跑 5~10 个交易日；
2. 改参数为 B，`rule-version: v3`，再跑 5~10 个交易日；
3. 用第 2 条 SQL 按 `rule_version` 分组对比。

同一个 `rule_version` 只对应一套参数，不要在参数不变的情况下改版本号，也不要改了参数不换版本号。

## 八、已知局限（别把结论用过头）

1. **只衡量次日 1 天**：尾盘策略通常是次日卖，超过 1 天的表现不在表里；如果实际持有 2~3 天，需要再加一个回填窗口。
2. **推荐价是 14:45 的快照价**：不是实际成交价，滑点、封单、买不到都没体现。
3. **量比/换手取自腾讯分时接口同一次响应里的 `qt` 实时行情块**（`qt[38]`=换手率、`qt[49]`=量比，是请求时刻的值），不再依赖收盘后才落库的 `stock_daily_quote`；只有接口没返回该块时才退回行情表，两者都取不到则不校验（分组备注里已注明）。
4. **分时数据来自腾讯非官方接口**：可能限流、字段变更；某只票抓取失败会被计为"抓取失败"而不是"不推荐"。
5. **样本积累慢**：推荐组每天最多 10 只，两周约 100 条；被挡组每天 300 条以上，对比结论来得更快，但推荐组自身的统计意义建议至少跑 20 个交易日。
6. **没有剔除大盘/板块影响**：普跌日的浮亏会被算到策略头上，对比时最好看"上涨占比"而不是只看平均涨幅。
7. **「数据不足 / 无昨收 / 抓取失败」不进记录表**：这三类没有可用指标，只体现在漏斗计数里；记录表里的被挡样本都是"指标算得出来、但没过闸门"的票。
8. **日志里的"推荐组/被挡组"是各取最近 300 条**，两者的时间窗口不一定对齐（被挡组一天就有 300 条，推荐组要一个月）；严谨对比请用第 6/7 条 SQL。
